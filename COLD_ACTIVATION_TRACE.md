# 23A355: owned-scene activation and a cold application process

Read-only firmware audit, 2026-11-02. Source: the already available iOS 26.0.1 / 23A355 arm64e dyld shared cache under `/workspace/firmware-research/dyld`; FrontBoard Objective-C metadata in `firmware-research/evidence/FrontBoard-verbose.txt`. No code was run in SpringBoard or on a phone. Addresses below belong to this cache only. Quiet, address/count-bounded disassembly was used; selector names were resolved from the Objective-C stub's selector-reference pointer and its pointed-to C string, not inferred from branch addresses.

## Finding

`FBScene` activation has an explicit internal path for an application that has no existing `FBProcess`, process handle, or scene remnant. It constructs its own execution context from the scene definition's nonlocal client identity, normalizes that context for scene activation, asks the workspace's process manager for a process future, and internally schedules bootstrap. The eventual bootstrap constructs and executes an `RBSLaunchRequest` when there is no existing process handle.

This supports removing the *source-scene dependency* from PPO's owned-scene definition, provided its audited bundle-identity factory produces a valid identity with `supportsLaunchingDirectly == YES`, and the normal audited UIKit containment/activation path is retained. PPO does not need to call any of the process bootstrap/launch selectors below. The analysis establishes a firmware call path, not successful on-device launch, RunningBoard admission, entitlement satisfaction, scene connection, or rendering on Dopamine/ElleKit.

## Exact call path and conditions

1. `-[FBScene activateWithTransitionContext:completion:]`, IMP `0x1a84290c4`, validates finished initialization / no concurrent update / no deactivation and calls helper `0x1a842945c` at `0x1a842917c`. It later submits its settings update with `performUpdate:withCompletion:` at `0x1a84293d4`.
2. Helper `0x1a842945c` checks the main thread (`isMainThread`, call `0x1a84294ac`), returns success if already active, and rejects an invalidated scene. It asserts a workspace exists, no client handle exists, and a normal nonlegacy scene has no pre-existing client.
3. It reads `_definition` at FBScene offset `0x78`, sends `clientIdentity` (`0x1a8429558`), then tests `isLocal` (`0x1a8429564`). This trace follows **nonlocal** client identity and `_remnant == nil` (offset `0x80`, branch `0x1a8429570 -> 0x1a84295f4`). Local and remnant paths are different.
4. It reads the identity's `processIdentity` at `0x1a84295f8`. A supplied `transitionContext.clientProcessHandle` is checked against that identity and follows a handle-based path. With **no supplied handle**, normal settings (`isClientFuture == NO`) and target identity different from `identityOfCurrentProcess`, it enters `0x1a842972c`.
5. It obtains `transitionContext.executionContext` and `mutableCopy`. If none exists, `0x1a84297ec-0x1a8429800` allocates **FBMutableProcessExecutionContext** and calls `initWithIdentity:` with the scene definition's process identity. The class-reference at `0x1e7a30d98` points to class `0x1ed81f3a0`; FrontBoard metadata names that class. An existing context with nil identity receives `setIdentity:`; an existing mismatched identity asserts rather than silently replacing it.
6. It calls `copyOrUpdateForSceneActivationWithSettings:` at `0x1a8429818`. This normalizer is `-[FBProcessExecutionContext copyOrUpdateForSceneActivationWithSettings:]`, IMP `0x1a83ea650`. It chooses a launch intent from the existing context/settings, makes a mutable context if needed, and sets `forSceneActivation = YES` internally. PPO should not duplicate or guess its intent values.
7. The workspace at FBScene offset `0xf8` supplies its process manager through helper `0x1a83d4bdc` (loads workspace offset `0x8`). This offset is `_processManager` in FBSceneWorkspace metadata. It receives `_createProcessFutureWithExecutionContext:error:` at **`0x1a8429840`**.
8. `-[FBProcessManager _createProcessFutureWithExecutionContext:error:]`, IMP **`0x1a84241ec`**, is a small forwarder: moves error output to argument 4, sets `synchronously = 0`, and forwards to `_bootstrapProcessWithExecutionContext:synchronously:error:`.
9. `-[FBProcessManager _bootstrapProcessWithExecutionContext:synchronously:error:]`, IMP **`0x1a84253b0`**, copies the context, extracts its completion/identity, checks identity exists and **`supportsLaunchingDirectly`** (call **`0x1a8425444`**), then asks `processForIdentity:` (`0x1a84254ac`). Invalid/not-direct-launch identity takes an error path. Existing process uses that process. The no-existing-process path is `0x1a84257cc` onward: checks pending processes and manager invalidation, obtains identity.`fb_processClass` (`0x1a84259b8`), allocates it, and calls `_initWithProcessManager:identity:handle:executionContext:` at **`0x1a84259d0`**, with **nil handle** (`x4 = 0`). It adds the process to the pending set and invokes `_bootstrap_consumeLock_addProcess:synchronously:` at `0x1a84259fc`, preserving the original false synchronous flag.
10. `-[FBProcessManager _bootstrap_consumeLock_addProcess:synchronously:]`, IMP **`0x1a84262f8`**, routes the false case onto its `_bootstrapQueue` (offset `0x28`); block invoke **`0x1a84263f4`** then calls the same operation with synchronous true. The operation's no-flag method IMP `0x1a8426438` uses `bootstrapLock:` with block **`0x1a8426520`**. That block calls process.`bootstrapWithDelegate:` at **`0x1a8426588`**. This is internal queueing; the scene activation does not force synchronous process exec on SpringBoard's main thread.
11. `-[FBProcess bootstrapWithDelegate:]`, IMP **`0x1a8403ecc`**, marks bootstrap started / stores its delegate, then calls `_bootstrapAndExec` at **`0x1a8403f3c`**.
12. `-[FBProcess _bootstrapAndExec]`, IMP **`0x1a83d5770`**, builds its bootstrap context. It checks `_handle` (FBProcess offset `0x30`) at `0x1a83d5900-0x1a83d590c`. For **nil handle**, it enters **`0x1a83d5a40`**, allocates **RBSLaunchRequest**, initializes it with the bootstrap context via `initWithContext:` at **`0x1a83d5a50`**, and calls **`executeRequest` at `0x1a83d5a64`**. The class-reference at `0x1e6bc7470` points to class `0x1ed65d940`; class RO-name pointer `0x1f0447498 -> 0x18e67aaed` is `RBSLaunchRequest`. The response is inspected for process/error and has explicit retry/failure paths; executing the request does not imply success.

## What this does not require

The traced cold branch does not require an existing application's scene definition, an existing process handle, a scene remnant, or an external app-open command. It does not justify calling the transaction/process-manager/RBS APIs manually. `FBApplicationUpdateScenesTransaction` also owns a process-launch transaction, but it was unnecessary to establish this direct scene-activation path, and no PPO call to that transaction is proposed.

## Remaining runtime boundary

The factory audit must separately show that `identityForBundleID:` creates the intended installed embedded-application identity and passes the direct-launch condition. Runtime guards must still validate target IDs/eligibility, exact firmware/framework UUIDs, audited Objective-C encodings, owned identifiers, inactive-before-containment state, namespace/proxy ownership, and bounded owned-scene teardown. Cold process launch plus visible/interactable content on a real phone remains untested by this analysis. SpringBoard's built-in call path can still return a launch/connection error; PPO must report and clean up its own scene without altering a system-owned scene or terminating the application.
